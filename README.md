# Cold Drinks Wholesale Distribution App

A Flask application for managing a cold-drinks manufacturing & wholesale distribution
business: products, daily production, delivery routes, stores, route trips (dispatch →
per-store sales/collections → returns), and per-store credit ledgers.

See [`coldrink-distribution-app-spec.md`](coldrink-distribution-app-spec.md) for the full
functional spec this app implements.

## Tech Stack
- Flask (app factory) + Flask-SQLAlchemy + Flask-Migrate, deployed on **Vercel** as a
  serverless function, backed by **Supabase Postgres**.
- Flask-Login with a single shared login (no per-staff accounts — only the person doing
  office/data entry logs in).
- Server-rendered Jinja2 + Bootstrap 5, small vanilla JS for the trip-entry screen.

## Project Structure
```
app/
  __init__.py        app factory
  config.py           env-driven config (DB, secret key, admin credentials)
  extensions.py        db, migrate, login_manager, limiter, csrf
  models.py            Product, Production, Route, Store, RouteTrip, RouteTripItem,
                        StoreSale, Payment
  services/
    ledger.py           single-writer StoreSale + mirrored Payment, balance calculation
    reconciliation.py    advisory qty_sent vs qty_returned+sold mismatch checks
  auth.py, products.py, production.py, routes_bp.py, stores.py, trips.py, reports.py
templates/            one folder per blueprint above, plus base.html
static/                css/js
api/index.py           Vercel WSGI entrypoint (imports the app factory)
run.py                 local dev entrypoint
migrations/            Alembic migrations (generated by `flask db migrate`)
```

## Local Setup

1. **Create a Supabase project** (https://supabase.com) — free tier is enough to start.
   In *Project Settings → Database → Connection string*, copy:
   - the **Transaction pooler** URI (port 6543) → `DATABASE_URL`
   - the **Session pooler** or direct URI (port 5432) → `MIGRATION_DATABASE_URL`

2. **Virtual environment & dependencies**
   ```powershell
   python -m venv venv
   venv\Scripts\activate
   pip install -r requirements.txt
   ```

3. **Configure `.env`** (copy from `.env.example` if starting fresh):
   ```powershell
   python -c "import secrets; print(secrets.token_hex(32))"          # -> SECRET_KEY
   python -c "from werkzeug.security import generate_password_hash; print(generate_password_hash('your_password'))"   # -> ADMIN_PASSWORD_HASH
   ```
   Fill in `DATABASE_URL`, `MIGRATION_DATABASE_URL`, `SECRET_KEY`, `ADMIN_USERNAME`,
   `ADMIN_PASSWORD_HASH` in `.env`.

4. **Create the database schema** (run locally, against `MIGRATION_DATABASE_URL`):
   ```powershell
   set FLASK_APP=run.py
   flask db init         # first time only
   flask db migrate -m "initial schema"
   flask db upgrade
   ```

5. **Run the app locally**
   ```powershell
   python run.py
   ```
   Visit http://127.0.0.1:5000 and log in with `ADMIN_USERNAME` / the password you hashed.

## Migration Checklist (important — read before changing models.py)

Vercel's serverless functions cannot run `flask db upgrade` themselves (no reliable hook,
and concurrent cold starts racing to run DDL is unsafe). Whenever `app/models.py` changes:

1. Run `flask db migrate -m "..."` and `flask db upgrade` **locally**, against
   `MIGRATION_DATABASE_URL` (the direct/session connection, not the pooler).
2. Verify the change against the real Supabase database.
3. Only then deploy the code that depends on the new schema.

## Deploying to Vercel

1. Push this repo to GitHub, import it in the Vercel dashboard.
2. In Project Settings → Environment Variables, add `SECRET_KEY`, `DATABASE_URL`,
   `ADMIN_USERNAME`, `ADMIN_PASSWORD_HASH` (no need for `MIGRATION_DATABASE_URL` on
   Vercel — that's only used locally for migrations).
3. Deploy. `vercel.json` routes everything to `api/index.py`.

## Key Design Notes
- Products are priced in bulk (e.g. ₹160 per 100 units), but every production/dispatch/
  return/sale quantity is tracked in individual units, not fixed "packets" — stores don't
  always buy in clean multiples of the bulk size. `Product.price_per_unit` derives the
  per-unit rate from `bulk_price / bulk_size`, and every `StoreSale` snapshots that rate at
  the time of sale (`unit_price_snapshot`) so historical reports stay correct even if prices
  change later.
- Every `StoreSale.amount_collected` is mirrored into a `sale-linked` `Payment` row in the
  same transaction (`app/services/ledger.py`) — that's the only supported way to write
  sale-linked payments, so the ledger never drifts. Standalone/adjustment payments are
  entered directly from a store's profile page.
- `RouteTripItem.qty_returned` is `NULL` until entered (distinct from a confirmed `0`), so
  reconciliation warnings only appear once returns have actually been recorded — they never
  block saving.
- Route reports join through `RouteTrip.route_id`, not `Store.route_id`, so reassigning a
  store to a different route later doesn't misattribute historical trips.
